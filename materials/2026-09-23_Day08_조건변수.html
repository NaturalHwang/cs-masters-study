1. 오늘의 주제

Day07에서 Mutex를 사용해 Critical Section에 한 번에 한 Thread만 들어가도록 만들었습니다. 하지만 동시성 프로그램에는 또 다른 종류의 문제가 있습니다. 공유 상태는 안전하게 볼 수 있지만, 지금 당장은 진행 조건이 만족되지 않아 기다려야 하는 경우입니다.

오늘은 조건 변수(Condition Variable), wait, signal/notify, 조건 재검사, 그리고 하나의 작은 Producer/Consumer Queue를 통해 이 문제를 배웁니다.

핵심 구분: Mutex는 “동시에 들어가지 못하게” 하고, Condition Variable은 “상태가 바뀔 때까지 효율적으로 기다리게” 합니다.

2. 학습 목표

  • Queue와 Producer/Consumer 문제를 작은 예제로 설명할 수 있다.
  • Condition Variable이 Mutex와 다른 목적의 동기화 도구임을 설명할 수 있다.
  • wait()가 Mutex를 놓고 잠든 뒤, 깨어날 때 다시 Mutex를 획득하는 흐름을 추적할 수 있다.
  • 깨어난 뒤 조건을 반드시 while로 재검사해야 하는 이유를 설명할 수 있다.

3. 이전 학습과의 연결

Day06 Race Condition / Atomicity ↓ Day07 Critical Section + Mutex “공유 상태를 안전하게 본다” ↓ Day08 Condition Variable “상태가 원하는 조건이 될 때까지 기다린다”

Mutex만 있으면 Queue가 비어 있는지 안전하게 검사할 수 있습니다. 하지만 Queue가 비어 있다면 Consumer는 언제 다시 검사해야 하는가? 이것이 오늘의 중심 문제입니다.

4. 필요한 선수지식과 3~5분 복습

4.1 Queue란?

Queue는 데이터를 줄처럼 넣고 빼는 자료구조입니다. 오늘은 가장 단순하게 capacity = 1인 Queue를 사용합니다.

Producer -- put(item) --> [ Queue ] -- get() --> Consumer Queue 비어 있음: count = 0 Queue 가득 참: count = 1

일반적으로 FIFO(First In, First Out)를 떠올리면 되지만, 오늘의 핵심은 자료구조 알고리즘이 아니라 비었는지/가득 찼는지라는 상태 조건입니다.

4.2 Mutex 복습

lock(mutex)
// shared state 확인/변경
unlock(mutex)

Mutex는 count와 Queue를 여러 Thread가 동시에 망가뜨리지 않게 보호합니다.

4.3 오늘의 두 Predicate

Predicate는 “지금 진행해도 되는가?”를 판단하는 참/거짓 조건입니다.

  • Consumer가 진행할 조건: count > 0 — Queue가 비어 있지 않다.
  • Producer가 진행할 조건: count < capacity — Queue가 가득 차지 않았다.
깊이 제한: 오늘은 Semaphore를 해결책으로 섞지 않습니다. Semaphore는 Day09에서 목적과 상태 표현 방식의 차이를 별도로 비교합니다.

5. 먼저 제시하는 문제 상황

Consumer가 Queue에서 작업을 가져가려는데 Queue가 비어 있다고 합시다.

lock(mutex)
if queue is empty:
    ???
item = queue.remove()
unlock(mutex)

가장 단순한 생각은 반복해서 확인하는 것입니다.

while true:
    lock(mutex)
    if queue is not empty:
        item = queue.remove()
        unlock(mutex)
        break
    unlock(mutex)

이 방식은 Busy Waiting입니다. 실제 할 일이 없는 동안에도 계속 CPU를 얻어 Lock을 잡고 상태를 확인합니다.

더 큰 문제는 “기다리는 동안 Mutex를 계속 잡고 있자”는 잘못된 해결책입니다.

lock(mutex)
while queue is empty:
    // mutex를 잡은 채 기다림  ← 문제
왜 문제인가? Producer도 Queue에 item을 넣으려면 같은 Mutex가 필요합니다. Consumer가 Mutex를 놓지 않으면 Producer가 상태를 바꿀 수 없어 영원히 기다릴 수 있습니다.

6. 핵심 개념 — 직관 → 예 → 정의 → 동작

6.1 Condition Variable의 직관

Condition Variable은 “이 Predicate가 지금 false니까, 다른 Thread가 상태를 바꾸었다고 알려줄 때까지 나는 잠들겠다”를 표현하는 도구입니다.

Condition Variable 자체가 조건 값을 저장하는 것은 아닙니다. 실제 조건은 count > 0 같은 공유 상태 기반 Predicate이고, Condition Variable은 그 상태 변화에 맞춰 기다리고 깨우는 통로입니다.

6.2 wait의 핵심 동작

전형적인 Condition Variable의 wait(cv, mutex)는 호출할 때 Mutex를 이미 가지고 있어야 합니다.

Consumer가 mutex 보유 ↓ Predicate 확인: count == 0 ↓ wait(cv, mutex) ├─ mutex를 놓음 └─ waiting 상태로 잠듦 (이 전환이 경쟁을 만들지 않도록 결합됨) ↓ Producer가 mutex 획득 가능 ↓ Producer가 item 추가 + signal ↓ Consumer가 깨어남 ↓ consumer는 mutex를 다시 획득한 뒤 wait에서 돌아옴 ↓ Predicate 재검사

POSIX의 pthread_cond_wait() 같은 API에서는 wait가 Mutex를 원자적으로 놓으면서 Block하고, 성공적으로 돌아올 때 Mutex를 다시 소유합니다.

6.3 signal / notify

signal 또는 언어에 따라 notify는 기다리는 Thread 중 하나가 다시 실행 가능해지도록 깨우는 동작입니다.

하지만 “signal을 받았다 = Predicate가 반드시 true다”는 뜻이 아닙니다. signal은 상태가 바뀌었으니 다시 확인할 기회가 생겼다는 신호에 가깝습니다.

6.4 왜 if가 아니라 while인가?

다음 코드는 위험합니다.

lock(mutex)
if queue is empty:
    wait(notEmpty, mutex)
item = queue.remove()
unlock(mutex)

Thread가 깨어난 뒤 Queue가 여전히 비어 있을 수 있습니다. 예를 들어 Consumer C1과 C2가 모두 기다리고 있고 C1이 먼저 item을 가져가면, C2가 Mutex를 다시 얻었을 때는 이미 Queue가 비어 있을 수 있습니다. 구현에 따라 spurious wakeup도 허용될 수 있습니다.

따라서 안전한 기본 형태는 다음입니다.

lock(mutex)
while queue is empty:
    wait(notEmpty, mutex)
item = queue.remove()
unlock(mutex)
기억할 패턴: “깨어났으니 진행”이 아니라 “깨어났으니 Lock을 가진 상태에서 Predicate를 다시 검사”입니다.

6.5 Producer / Consumer — capacity 1 Queue

하나의 Queue와 두 개의 상태 조건을 사용합니다.

// shared
queue capacity = 1
mutex
notEmpty   // consumer가 기다림
notFull    // producer가 기다림

producer(item):
    lock(mutex)
    while queue is full:
        wait(notFull, mutex)
    queue.add(item)
    signal(notEmpty)
    unlock(mutex)

consumer():
    lock(mutex)
    while queue is empty:
        wait(notEmpty, mutex)
    item = queue.remove()
    signal(notFull)
    unlock(mutex)
    return item

Producer가 item을 넣으면 “이제 empty가 아닐 수 있다”고 Consumer를 깨웁니다. Consumer가 item을 빼면 “이제 full이 아닐 수 있다”고 Producer를 깨웁니다.

6.6 작은 실행 추적

순서Consumer CProducer PQueueMutex
1lock, empty 확인[]C
2wait(notEmpty) → mutex 놓고 잠듦[]해제
3waitinglock[]P
4waitingitem X 추가[X]P
5깨울 대상이 됨signal(notEmpty), unlock[X]해제

7. 실제 시스템 사례

POSIX Threads의 Condition Variable API는 오늘 배운 구조를 직접 보여줍니다.

  • pthread_cond_wait(cond, mutex): Mutex를 가진 상태에서 호출하고, Mutex를 놓으면서 Block한 뒤 돌아오기 전에 Mutex를 다시 획득합니다.
  • pthread_cond_signal(cond): 해당 Condition Variable에서 기다리는 Thread 중 하나를 깨울 수 있습니다.
  • pthread_cond_broadcast(cond): 기다리는 Thread들을 모두 깨우는 용도로 사용됩니다.

POSIX 문서도 Condition Variable과 연결된 Boolean Predicate를 wait 이후 다시 평가해야 한다고 설명합니다. 즉, Predicate가 진실의 원천(SSoT)이고 wakeup 자체를 상태로 취급하면 안 됩니다.

주의: 구체적인 wakeup 순서나 어떤 Thread가 먼저 Mutex를 다시 얻는지는 구현과 scheduler에 따라 달라질 수 있으므로 코드가 특정 순서를 가정하면 안 됩니다.

8. Trade-off와 대안

접근장점대가/위험
Busy Waiting구조가 단순할 수 있음조건이 오래 false면 CPU를 낭비하고 Lock 경쟁 증가
Condition Variable조건이 false인 동안 Thread를 Block시켜 효율적으로 기다림Predicate·Mutex·signal 관계를 정확히 설계해야 함
signal/notify one필요한 수만 깨워 wakeup 비용을 줄일 수 있음잘못된 종류의 waiter를 깨우는 설계면 진행이 꼬일 수 있음
broadcast/notify all조건을 만족할 수 있는 여러 waiter에게 재검사 기회 제공많은 Thread가 동시에 깨어 Lock을 경쟁하는 비용 가능

오늘의 핵심 설계 원칙은 “무조건 signal이 좋다/broadcast가 좋다”가 아니라 어떤 상태 변화가 어떤 waiter들의 Predicate를 true로 만들 수 있는가를 기준으로 선택하는 것입니다.

9. 간단한 심화

9.1 Condition Variable은 이벤트 저장소가 아니다

Condition Variable을 “signal 개수를 쌓아두는 상자”처럼 생각하면 안 됩니다. 기다리는 Thread가 없을 때 signal이 발생했다고 해서, 나중에 들어온 waiter가 과거 signal을 소비한다고 일반화할 수 없습니다.

따라서 올바른 프로그램은 항상 공유 상태의 Predicate를 먼저 확인합니다.

9.2 Lost Wakeup을 피하는 구조

“조건 검사 → wait 진입” 사이에 Producer가 상태를 바꾸고 signal을 보내면 signal을 놓칠 수 있지 않을까?”라는 걱정이 생깁니다. 그래서 Condition Variable wait는 같은 Mutex와 함께 사용되고, Mutex를 놓고 Block하는 전환이 경쟁을 만들지 않도록 정의됩니다.

정리: shared predicate를 Mutex로 보호하고, wait는 그 Mutex를 원자적으로 release+sleep하며, wakeup 후 Mutex를 다시 획득하고 Predicate를 while로 재검사합니다.

10. 핵심 요약

  1. Mutex는 공유 상태 접근을 보호하고, Condition Variable은 원하는 상태가 될 때까지 기다리는 문제를 해결합니다.
  2. Condition Variable의 진짜 조건은 queue not empty 같은 공유 상태 Predicate입니다.
  3. wait(cv, mutex)는 Mutex를 놓고 Block하며, 돌아오기 전에 Mutex를 다시 획득하는 형태로 사용됩니다.
  4. Wakeup은 조건이 true라는 보장이 아니므로 Predicate를 while로 재검사해야 합니다.
  5. Producer/Consumer에서는 상태 변화 뒤 적절한 waiter에게 signal/notify하여 진행 기회를 줍니다.

11. 확인 질문 3~5개와 접이식 해설

Q1. Mutex가 있는데 Condition Variable이 왜 또 필요한가?

해설 보기

Mutex는 “동시에 접근하지 않기”를 해결하지만, 지금 Predicate가 false일 때 “언제까지 어떻게 기다릴지”는 해결하지 않습니다. Condition Variable은 상태가 바뀔 때까지 Thread를 Block시켜 기다리도록 합니다.

Q2. Consumer가 Queue가 비어 있을 때 Mutex를 잡은 채 잠들면 왜 문제가 되는가?

해설 보기

Producer도 같은 Mutex가 있어야 Queue에 item을 넣을 수 있다면, Producer가 상태를 바꾸지 못합니다. 그래서 wait는 기다리는 동안 Mutex를 놓아야 합니다.

Q3. 왜 if empty: wait()보다 while empty: wait()가 안전한가?

해설 보기

깨어난 뒤 다른 Consumer가 먼저 item을 가져갈 수 있고, 구현에 따라 spurious wakeup도 가능하기 때문입니다. Wakeup은 Predicate가 true라는 보장이 아니므로 Mutex를 다시 가진 상태에서 재검사해야 합니다.

Q4. 3~5분 실행 추적

capacity=1 Queue가 비어 있고 Consumer C1, C2가 모두 notEmpty에서 기다립니다. Producer가 item X 하나를 넣고 waiter 하나를 깨웁니다. 이후 C1이 X를 가져간 다음, 어떤 이유로 C2도 wait에서 돌아왔다고 합시다. C2가 while 대신 if를 사용했다면 어떤 잘못된 실행이 가능할까요?

해설 보기

C2가 “이미 wait에서 돌아왔으니 item이 있다”고 가정하고 빈 Queue에서 remove를 시도할 수 있습니다. while이면 C2가 Mutex를 가진 상태에서 empty Predicate를 다시 검사하고 다시 wait합니다.

Q5. 설계 비교 — Busy Waiting vs Condition Variable

Queue에 item이 보통 수백 ms 뒤에 들어오는 시스템이라면 두 방식이 CPU 사용과 응답 준비 상태 측면에서 어떤 trade-off가 있을지 설명해보세요.

해설 보기

Busy Waiting은 기다리는 동안 반복 검사로 CPU 시간을 소비할 수 있습니다. Condition Variable은 waiter를 Block시켜 CPU를 다른 작업에 쓸 수 있지만, wakeup·scheduling·Mutex 재획득 비용과 더 정확한 동기화 설계가 필요합니다.

12. 연구자의 관점

  • Wakeup efficiency: 어떤 Thread를 몇 개 깨워야 불필요한 contention을 줄이면서 progress를 보장할 수 있는가?
  • Correctness testing: 드문 interleaving, spurious wakeup, signal timing을 테스트에서 어떻게 재현할 수 있는가?
  • Observability: waiter 수, wakeup 횟수, Lock 대기 시간을 어떻게 관찰하면 synchronization bottleneck을 찾을 수 있는가?

이 관점은 이후 Software Engineering의 concurrency testing, deterministic scheduling, observability 연구와 연결될 수 있습니다.

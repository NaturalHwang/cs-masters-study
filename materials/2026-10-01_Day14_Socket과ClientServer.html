1. 오늘의 주제

오늘은 Socket, Port, Client/Server, Connect/Send/Receive, Serialization, Message Boundary를 연결한다.

5. 문제 상황

한 서버 컴퓨터에서 웹 서비스, 원격 접속 서비스, 재고 예약 서비스가 동시에 동작할 수 있다. IP Address만으로는 “그 컴퓨터”까지는 찾아가도, 그 안의 어느 네트워크 서비스가 데이터를 받아야 하는지가 남는다.

핵심: Transport protocol과 Port가 통신 끝점을 구분하는 데 사용된다.

6. 핵심 개념 — 직관 → 예 → 정의 → 동작

6.1 Socket

Socket은 애플리케이션이 OS의 네트워크 스택을 사용할 때 잡는 통신 끝점(endpoint) 또는 핸들(handle)로 생각할 수 있다.

Application
   ↓ Socket interface
Operating System
   ↓ TCP or UDP
   ↓ IP
Network

6.2 Port

Port는 transport 계층에서 통신 끝점을 구분하는 번호다. “Port = Process 번호”라고 외우는 것은 부정확하다. 하나의 Process가 여러 Socket을 사용할 수 있다.

6.3 Client와 Server

Server는 보통 특정 주소와 Port에서 연결이나 메시지를 기다리고, Client는 상대 주소와 Port를 사용해 통신을 시작한다.

TCP Server의 개념 흐름은 주소 준비 → 수신 대기 → 연결 수락 → 데이터 송수신이고, Client는 연결 요청 → 데이터 송수신 흐름으로 이해하면 된다.

6.4 Connect / Send / Receive

Connect는 TCP 연결을 형성하는 단계, Send는 바이트를 송신 쪽 스트림에 제공하는 단계, Receive는 도착해 이용 가능한 바이트를 읽는 단계로 볼 수 있다.

중요: 애플리케이션의 한 번의 Send와 상대의 한 번의 Receive가 1:1로 대응한다고 가정하면 안 된다.

6.5 왜 메시지 경계가 필요한가?

Client가 논리적으로 두 메시지를 보냈다고 하자.

Message A: RESERVE 42
Message B: COUNT 1

TCP는 이 둘을 “Message A, Message B”라는 단위가 아니라 연속된 바이트로 본다. 따라서 수신 측에서는 일부만 먼저 보거나 여러 논리 메시지의 바이트가 함께 보이는 상황을 처리해야 한다.

6.7 Serialization

네트워크로 직접 객체를 보내는 것이 아니라 결국 bytes를 보낸다. 따라서 애플리케이션 데이터 구조를 bytes 표현으로 바꾸는 과정이 필요하다.

ReservationRequest
  productId = 42
  quantity  = 1
       ↓ serialization
{"productId":42,"quantity":1}
       ↓ encoding
bytes

JSON, Protocol Buffers 같은 형식은 서로 다른 serialization 선택지다.

6.8 UDP Socket과 메시지 경계

UDP에서는 Datagram 단위가 유지된다. 그러나 손실·재정렬 같은 UDP의 특성은 그대로 고려해야 한다.

7. 실제 시스템 사례

재고 예약 서비스가 TCP 위에서 Length Prefix + JSON을 사용한다고 하자.

[payload length][JSON payload]

{"requestId":"r-1001","productId":42,"quantity":1}

서버는 먼저 길이 정보를 확보하고, 그 길이만큼 payload bytes가 모일 때까지 수신 버퍼를 관리한 뒤 하나의 요청을 복원한다. 그 후 deserialize해서 비즈니스 로직에 넘긴다.

이 흐름은 “한 번 Receive = 한 요청”이라는 잘못된 가정을 피하게 해준다.

9. 간단한 심화

TCP 연결은 개념적으로 (source IP, source port, destination IP, destination port)의 조합으로 생각하면 이해하기 쉽다. 그래서 여러 Client가 같은 Server Port에 동시에 연결할 수 있다.

실제 OS 내부의 wildcard binding, IPv4/IPv6, 주소 변환 같은 세부 동작은 오늘 범위를 넘는다.

10. 핵심 요약

  1. Socket은 애플리케이션과 OS 네트워크 기능 사이의 통신 끝점이다.
  2. IP와 Port는 서로 다른 수준의 목적지를 구분한다.
  3. TCP Client/Server는 연결 형성 후 byte stream을 송수신한다.
  4. TCP의 Send/Receive 호출 경계는 애플리케이션 메시지 경계가 아니다.
  5. Serialization과 Framing으로 bytes 위에 의미 있는 메시지를 만든다.

11. 확인 질문 3~5개와 접이식 해설

Q1. IP Address만으로 특정 서버 프로그램을 구분하기 어려운 이유는?

해설 보기

한 호스트에서 여러 네트워크 서비스가 동시에 동작할 수 있기 때문이다. Port 등 transport 수준의 구분 정보가 필요하다.

Q2. TCP에서 두 번 Send하면 상대도 반드시 두 번 Receive해야 같은 단위로 받는가?

해설 보기

아니다. TCP는 byte stream이라 애플리케이션 호출 경계를 보존하지 않는다.

Q3. Serialization과 Framing의 차이는?

해설 보기

Serialization은 데이터 구조를 bytes 표현으로 바꾸는 문제이고, Framing은 연속된 bytes에서 한 메시지의 시작과 끝을 구분하는 문제다.

Q4. 3~5분 실행 추적

길이 5의 payload HELLO를 받는다고 하자. 첫 수신에서 HE, 두 번째에서 L, 세 번째에서 LO와 다음 메시지 일부가 함께 들어왔다. 서버가 유지해야 할 상태를 설명해 보라.

해설 보기

현재 frame의 기대 payload 길이와 현재까지 누적한 bytes를 기억해야 한다. 정확히 5 bytes가 모이면 HELLO를 완성하고, 남은 bytes는 다음 frame 처리에 사용한다.

Q5. 여러 Client가 같은 Server Port에 동시에 연결할 수 있는 이유는?

해설 보기

연결은 source/destination IP와 Port의 조합으로 서로 구분될 수 있기 때문이다.

12. 연구자의 관점

  • Correctness: partial read와 framing 오류는 정상적인 byte-stream 처리에서도 발생할 수 있다.
  • Performance: buffer 크기, serialization 형식, 호출 횟수는 latency와 throughput에 영향을 줄 수 있다.
  • Robustness: length-prefix 방식에서는 길이값을 검증해 비정상적으로 큰 입력으로 인한 과도한 자원 사용을 막아야 한다.
  • Observability: 요청 ID와 연결 식별 정보를 함께 기록하면 네트워크 흐름과 애플리케이션 요청을 연결해 분석하기 쉽다.

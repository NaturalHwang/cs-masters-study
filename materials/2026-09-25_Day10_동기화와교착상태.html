1. 오늘의 주제

Week 2에서는 공유 상태가 잘못되는 문제와, 그 문제를 다루는 기본 동기화 도구를 순서대로 배웠습니다.

Day06 Race Condition / Atomicity / Invariant ↓ Day07 Critical Section / Mutex ↓ Day08 Condition Variable / Wait / Notify / Predicate 재검사 ↓ Day09 Semaphore / Permit / Acquire / Release ↓ Day10 “도구를 골랐는데도 왜 진행이 멈출 수 있는가?” → Deadlock

오늘은 새 동기화 primitive를 추가하지 않습니다. 대신 어떤 문제에 어떤 도구를 쓰는지를 다시 정리하고, 두 Lock만 사용하는 작은 교착 상태를 직접 추적합니다.

2. 학습 목표

  • Mutex, Condition Variable, Semaphore를 목적 기준으로 구분할 수 있다.
  • 두 Lock의 획득 순서가 달라질 때 Deadlock이 생기는 실행을 단계별로 추적할 수 있다.
  • 일관된 Lock Ordering이 왜 Deadlock 위험을 줄이는지 설명할 수 있다.
  • Safety와 Liveness를 직관적으로 구분하고 Deadlock이 어느 쪽을 깨는지 설명할 수 있다.

4. 필요한 선수지식과 3~5분 복습

4.1 Mutex

특정 Critical Section에 한 번에 하나의 Thread만 들어가게 합니다. 목적은 상호 배제(Mutual Exclusion)입니다.

4.2 Condition Variable

공유 상태의 Predicate가 true가 될 때까지 기다릴 때 사용합니다. 일반적인 패턴은 Mutex로 상태를 보호하며 wait() 중 Mutex를 놓고, 깨어난 뒤 다시 획득해서 조건을 재검사하는 것입니다.

4.3 Semaphore

permit 수를 관리해서 동시에 진행 가능한 실행 수나 동일 자원 수를 제한합니다. permit이 없으면 기다리고, 반환되면 다시 진행할 수 있습니다.

4.4 오늘 사용할 두 Lock

재고 예약 서비스가 학습용으로 두 공유 자원을 보호한다고 합시다.

  • stockLock: 재고 상태 보호
  • reservationLock: 예약 목록 상태 보호
깊이 제한: 오늘은 두 Lock만 사용합니다. Deadlock detection, wait-for graph 알고리즘, Banker’s Algorithm, priority inversion, distributed deadlock은 심화로 넘깁니다.

5. 먼저 제시하는 문제 상황

두 작업이 각각 두 Lock이 필요하지만 획득 순서가 반대라고 합시다.

Thread A:
    lock(stockLock)
    ...
    lock(reservationLock)
    ...
    unlock(reservationLock)
    unlock(stockLock)

Thread B:
    lock(reservationLock)
    ...
    lock(stockLock)
    ...
    unlock(stockLock)
    unlock(reservationLock)

각 Thread는 자기 코드만 보면 “필요한 Lock을 잡고 작업한다”는 정상적인 코드처럼 보입니다. 하지만 다음 실행이 가능합니다.

순서Thread AThread B결과
1stockLock 획득A가 stockLock 보유
2reservationLock 획득B가 reservationLock 보유
3reservationLock 요청A는 B가 놓기를 기다림
4stockLock 요청B는 A가 놓기를 기다림
A holds stockLock A waits for reservationLock ─────┐ │ ▼ B holds reservationLock B waits for stockLock ───────────┘ 둘 다 “상대가 먼저 놓아야” 진행 가능 하지만 둘 다 기다리느라 놓지 못함

이 상태가 교착 상태(Deadlock)입니다.

6. 핵심 개념 — 직관 → 예 → 정의 → 동작

6.1 Deadlock의 직관

Deadlock은 여러 실행 주체가 서로가 가진 자원을 기다리면서 아무도 앞으로 진행할 수 없는 상태입니다.

핵심: “느리게 진행한다”가 아니라 현재 기다림 관계가 해소되지 않는 한 스스로는 진행할 수 없다는 점이 중요합니다.

6.2 작은 정의

두 Thread와 두 Lock만 생각하면 다음 조건이 핵심입니다.

  • A가 Lock 1을 보유한 채 Lock 2를 기다림.
  • B가 Lock 2를 보유한 채 Lock 1을 기다림.
  • 각 Thread가 기다리는 동안 현재 보유 Lock을 놓지 않음.

그러면 기다림이 원(Cycle)을 이루며 진행이 멈춥니다.

6.3 Deadlock을 만드는 네 조건 — 오늘은 이름만 연결

고전적으로 Deadlock과 관련해 다음 네 조건이 함께 언급됩니다. 오늘은 두-Lock 예제에 연결하는 수준으로만 봅니다.

조건두-Lock 예제에서의 의미
Mutual Exclusion한 Lock은 한 시점에 한 Thread만 보유
Hold and Wait이미 Lock 하나를 보유한 채 다른 Lock을 기다림
No Preemption다른 Thread가 보유 Lock을 강제로 뺏지 않음
Circular WaitA→B의 Lock을 기다리고 B→A의 Lock을 기다림

이 네 조건을 모두 외우는 것보다 오늘은 원형 기다림(Circular Wait)을 눈으로 찾는 것이 더 중요합니다.

6.4 해결 직관: 일관된 Lock Ordering

모든 코드가 Lock을 항상 같은 순서로 획득하도록 규칙을 정할 수 있습니다.

공통 규칙:
1. stockLock
2. reservationLock

Thread A:
    lock(stockLock)
    lock(reservationLock)

Thread B:
    lock(stockLock)
    lock(reservationLock)

B가 먼저 reservationLock을 잡는 경로가 사라지므로, 위의 두-Lock 원형 기다림을 만들 수 없습니다.

설계 원칙: 여러 Lock이 필요한 코드에서는 “각 함수가 알아서 잡는 순서”가 아니라 시스템 전체가 공유하는 순서 규칙이 필요합니다.

6.5 Safety와 Liveness 직관

관점직관Week 2 예시
Safety“나쁜 일이 일어나지 않는다”재고 1개인데 예약 2건 성공하지 않는다
Liveness“좋은 일이 결국 진행된다”기다리던 예약 요청이 언젠가 처리된다

Mutex로 Race Condition을 막아 Safety를 지키더라도, Lock을 잘못 조합하면 Deadlock으로 Liveness를 잃을 수 있습니다.

중요: Safety와 Liveness는 서로 같은 말이 아닙니다. “잘못된 결과가 나오지 않는다”와 “시스템이 계속 진행한다”는 별도 질문입니다.

7. 실제 시스템 사례

7.1 다중 자원 업데이트

실제 서버에서는 하나의 요청이 여러 공유 구조를 함께 갱신할 수 있습니다. 예를 들어 메모리 캐시와 세션 상태, 두 개의 내부 Registry, 여러 파일 또는 장치 상태를 순차적으로 잠글 수 있습니다.

서로 다른 코드 경로에서 Lock 획득 순서가 뒤집히면 테스트에서는 잘 드러나지 않다가 특정 Timing에서 Deadlock이 발생할 수 있습니다.

7.2 POSIX Mutex의 관점

POSIX Mutex의 기본 의미는 Lock이 사용 가능하지 않으면 호출 Thread가 기다릴 수 있다는 것입니다. 여러 Mutex를 중첩해 잡을 때 그 대기 관계는 애플리케이션의 Lock 획득 순서에서 생깁니다.

따라서 “Mutex 자체가 잘못되었다”기보다 여러 Mutex를 조합한 프로토콜이 Liveness 문제를 만들 수 있습니다.

실제 시스템과 학습 모델 구분: 실제 런타임은 mutex type, timeout, try-lock, scheduling, cancellation 등 더 많은 동작을 가질 수 있습니다. 오늘 모델은 blocking lock 두 개의 가장 단순한 Deadlock만 다룹니다.

8. Trade-off와 대안

방법장점대가 / 주의
일관된 Lock Ordering원형 대기를 구조적으로 줄임, 규칙이 명확전역 순서를 문서화·준수해야 함
Lock 범위 축소동시에 여러 Lock을 보유하는 시간을 줄일 수 있음너무 줄이면 Atomicity/Invariant가 깨질 수 있음
Try-lock + 실패 시 해제/재시도영구 대기 회피 가능재시도 정책·공정성·Starvation이 복잡해질 수 있음
공유 상태/Lock 수 자체 감소Deadlock 가능 구조를 단순화설계 변경·복사·메시지 전달 비용 가능

중요: “Lock을 없애면 성능이 좋아진다”거나 “Lock을 많이 쓰면 안전하다”처럼 단순화하면 안 됩니다. 지켜야 할 Invariant와 필요한 Liveness를 함께 봐야 합니다.

9. 간단한 심화 — Deadlock과 Starvation은 다르다

Deadlock에서는 기다림 관계 때문에 관련 Thread들이 서로 진행하지 못합니다.

Starvation은 시스템 전체는 진행하지만 특정 Thread가 계속 기회를 얻지 못하는 상황입니다. 예를 들어 Lock 경쟁에서 같은 Thread들이 계속 먼저 획득하고 어떤 Thread만 오랫동안 획득하지 못할 수 있습니다.

DeadlockStarvation
전체 진행관련 집합이 멈춤다른 Thread는 진행 가능
핵심 원인순환 기다림 등불공정한 자원 배분/스케줄링 등
Liveness명확히 위반특정 Thread 관점에서 위반 가능

오늘은 둘을 구분하는 것까지만 하고, 공정성(Fairness) 보장은 이후 필요한 시점에 다시 다룹니다.

10. 핵심 요약

  1. Mutex, Condition Variable, Semaphore는 서로 다른 동기화 문제를 표현한다.
  2. Deadlock은 여러 Thread가 서로 필요한 자원을 기다리며 아무도 진행하지 못하는 상태다.
  3. 두 Lock을 서로 반대 순서로 획득하면 Circular Wait가 만들어질 수 있다.
  4. 일관된 Lock Ordering은 작은 두-Lock Deadlock을 예방하는 대표적 설계 규칙이다.
  5. Safety는 잘못된 상태를 막는 문제이고, Liveness는 시스템이 결국 진행하는 문제다.

11. 확인 질문 3~5개와 접어서 보는 해설

Q1. 다음 요구사항에 가장 직접적으로 맞는 도구를 고르세요.

  1. 공유 카운터 갱신 Critical Section에 한 Thread만 들어가게 한다.
  2. Queue가 비어 있으면 Consumer가 item이 생길 때까지 기다린다.
  3. 외부 API 호출을 동시에 최대 8개까지만 허용한다.
해설 보기

1은 Mutex, 2는 Condition Variable(공유 Predicate + Mutex), 3은 Counting Semaphore가 목적을 가장 직접적으로 표현합니다.

흔한 오해: 세 도구 모두 Thread를 기다리게 할 수 있다는 이유만으로 서로 대체 가능한 동일 도구라고 보는 것.

Q2. Deadlock은 Race Condition과 같은 문제인가?

해설 보기

아닙니다. Race Condition은 실행 순서에 따라 올바르지 않은 결과가 나오는 문제이고, Deadlock은 기다림 관계 때문에 진행이 멈추는 Liveness 문제입니다. 동기화를 잘못 설계하면 Race를 막는 과정에서 Deadlock을 만들 수도 있습니다.

Q3. Safety는 지켜지는데 Liveness가 깨질 수 있는가?

해설 보기

가능합니다. 두 Thread가 Deadlock에 빠지면 공유 데이터가 잘못 갱신되는 일은 없을 수 있지만, 요청이 영원히 완료되지 않습니다. 즉 “잘못된 결과는 안 나옴”과 “결국 진행함”은 별개입니다.

Q4. 3~5분 실행 추적 — Deadlock 찾기

아래 순서대로 실행됩니다.

1. A: lock(L1) 성공
2. B: lock(L2) 성공
3. A: lock(L2) 시도
4. B: lock(L1) 시도

각 단계 뒤 A/B가 보유한 Lock과 기다리는 Lock을 표로 적어보고, 4번 뒤 누가 어떤 행동을 해야 현재 상태가 풀리는지 생각해보세요.

실행 추적 해설 보기
Thread보유대기
AL1L2
BL2L1

blocking lock만 사용하고 Thread가 기다리는 동안 보유 Lock을 자동으로 놓지 않는다면, 둘 다 자기 코드의 다음 단계로 갈 수 없습니다. 외부 개입이나 다른 설계가 없는 한 현재 기다림은 스스로 해소되지 않습니다.

Q5. 설계 비교 — 어떤 코드가 더 안전한 Lock 순서를 가지는가?

// A
function f1():
    lock(L1)
    lock(L2)

function f2():
    lock(L2)
    lock(L1)

// B
function f1():
    lock(L1)
    lock(L2)

function f2():
    lock(L1)
    lock(L2)
해설 보기

B가 두-Lock Circular Wait를 피하는 데 더 유리합니다. 두 경로 모두 L1→L2의 동일한 순서를 따르므로 “A는 L1 보유/L2 대기, B는 L2 보유/L1 대기” 구조를 만들 수 없습니다.

주의: 이것이 모든 종류의 Liveness 문제를 자동 해결한다는 뜻은 아닙니다. 오늘 범위는 두 Lock의 순환 대기 예방입니다.

12. 연구자의 관점

  • Correctness specification: 시스템의 Safety invariant와 Liveness requirement를 각각 어떻게 명세할 것인가?
  • Concurrency bug reproducibility: Deadlock을 만드는 특정 interleaving을 테스트에서 어떻게 재현할 것인가?
  • Static/Dynamic analysis: 코드의 Lock Ordering 위반이나 잠금 그래프의 cycle을 자동으로 탐지할 수 있는가?
  • Observability: 운영 환경에서 “어떤 Thread가 어떤 Lock을 보유/대기 중인가”를 어떻게 기록해야 원인을 찾기 쉬운가?

이 관점은 이후 Software Engineering의 testing, observability, program analysis와 자연스럽게 연결됩니다.

1. 오늘의 주제

Week 2까지는 같은 Process 안에서 Thread들이 공유 메모리(Shared Memory)를 다루는 문제를 봤다. 이제 서로 다른 주소 공간과 컴퓨터 사이에서 데이터를 전달하는 Message Passing의 기초를 배운다.

2. 학습 목표

  • 객체와 네트워크를 흐르는 Byte를 구분한다.
  • Message와 Protocol을 설명한다.
  • Application / Transport / IP / Link의 역할을 책임 분리 관점에서 설명한다.
  • Shared Memory와 Message Passing을 비교한다.

3. 이전 학습과의 연결

같은 Process
Thread A ── Shared Memory ── Thread B

다른 Machine
Process A ── bytes / messages ──→ Process B

같은 Process에서는 메모리를 공유할 수 있지만 원격 Process의 Heap은 직접 읽을 수 없다. 따라서 정보를 명시적으로 표현해 보내야 한다.

4. 필요한 선수지식과 3~5분 복습

Byte

Byte는 보통 8bit 데이터 단위다. 문자열·숫자·객체는 전송 가능한 Byte 표현으로 바뀌어야 한다.

Address Space

Machine A의 메모리 주소는 Machine B에서 같은 객체를 가리키지 않는다.

Local Call vs Remote Communication

reserve(productId, 1)         // 로컬 함수 호출
"productId=42, quantity=1"   // 원격 전달을 위한 표현의 예

5. 먼저 제시하는 문제 상황

모바일 앱이 서버에 “상품 42번을 1개 예약”하라고 요청한다고 하자. 앱 내부 객체를 서버가 직접 볼 수 없으므로 다음 질문이 생긴다.

  1. 의미를 어떤 Byte 형식으로 표현할까?
  2. 수신자는 그 Byte를 어떻게 해석할까?
  3. 어느 컴퓨터·프로세스로 보낼까?
  4. 여러 네트워크 구간을 어떻게 지나갈까?

6. 핵심 개념

6.1 Message

Message는 애플리케이션이 하나의 의미 단위로 다루는 정보다.

ReserveRequest {
  productId = 42
  quantity = 1
}

논리적 Message와 아래 계층의 전송 단위는 항상 동일하지 않다.

6.2 Protocol

Protocol은 서로 독립적인 구현이 데이터의 형식, 의미, 순서, 동작을 맞추기 위한 약속이다. Byte가 도착해도 양쪽의 해석 규칙이 다르면 통신은 성공했다고 볼 수 없다.

6.3 Layering

계층오늘 기억할 책임예
Application업무 의미와 메시지 형식HTTP, DNS, 자체 프로토콜
Transport프로세스 간 데이터 전달에 필요한 기능TCP, UDP
Internet / IP목적지 host 쪽으로 packet 전달IP
Link직접 연결된 한 구간의 전달Ethernet, Wi‑Fi 계열

6.4 Encapsulation 직관

Application data
   ↓
Transport 정보 + data
   ↓
IP 정보 + transport data
   ↓
Link 정보 + IP packet
   ↓
전송

각 계층은 자신의 책임에 필요한 정보를 다룬다. Header 암기는 오늘 목표가 아니다.

6.5 Shared Memory vs Message Passing

Shared MemoryMessage Passing
정보 전달같은 상태를 읽고 씀Byte/Message를 보냄
대표 문제Race, synchronization, visibility지연, 손실 가능성, 직렬화, 상대 실패
경계공유 상태 경계가 흐려질 수 있음메시지 인터페이스가 명시적
중요: Message Passing을 써도 수신 서버 내부에서 여러 Thread가 같은 상태를 수정하면 Race Condition은 여전히 생길 수 있다.

서버는 클라이언트 객체 자체가 아니라 약속된 Byte 표현을 받아 애플리케이션 의미로 복원한다.

8. Trade-off와 대안

Shared Memory는 같은 메모리에서 빠르게 공유할 수 있는 경우가 있지만 동기화가 어렵다. Message Passing은 주소 공간·머신 경계를 넘을 수 있고 인터페이스가 분명해지지만 직렬화, 파싱, 전송 지연과 실패 문제를 추가한다.

Layering은 책임을 나누어 구현을 단순화하지만, 장애 분석 시 여러 계층을 함께 봐야 하고 각 계층의 처리 비용도 존재한다.

9. 간단한 심화

Protocol은 단순한 데이터 구조 정의가 아니다. 어떤 메시지를 먼저 보낼 수 있는지, 오류를 어떻게 표현하는지, 버전이 바뀌었을 때 어떻게 호환할지 같은 상호작용 규칙도 포함할 수 있다.

전송 성공 ≠ 업무 처리 성공. 요청 Byte가 상대 시스템에 도달하는 사건과 원격 비즈니스 로직이 성공하는 사건은 구분해야 한다.

10. 핵심 요약

  1. 원격 Process는 같은 Heap 객체를 직접 공유하지 않으므로 Byte 표현으로 통신한다.
  2. Message는 의미 단위, Protocol은 그 의미를 공유하기 위한 약속이다.
  3. Application / Transport / IP / Link는 전달 책임을 나눈다.
  4. Shared Memory와 Message Passing은 서로 다른 비용과 실패 형태를 가진다.
  5. 전송됨과 원격 업무 성공은 같은 뜻이 아니다.

11. 확인 질문 3~5개와 접이식 해설

Q1. 왜 클라이언트 객체를 서버가 그대로 읽을 수 없는가?

해설 보기

객체는 클라이언트 프로세스의 주소 공간에 있다. 서버는 그 메모리에 직접 접근할 수 없으므로 Byte로 표현해 전달해야 한다.

Q2. Byte가 정확히 도착하면 Protocol은 없어도 되는가?

해설 보기

아니다. Byte의 의미와 구조를 양쪽이 동일하게 해석하기 위한 약속이 필요하다.

Q3. Application과 Transport 역할을 구분해보라.

해설 보기

Application은 업무 의미와 메시지를 정하고, Transport는 프로세스 간 전송에 필요한 기능을 제공한다. 구체적인 TCP/UDP 차이는 Day13에서 본다.

Q4. 3~5분 실행 추적

1. Client 객체
2. ?
3. Transport
4. IP
5. ?
6. Server 비즈니스 로직

2와 5에 어떤 변환이 필요한지 설명해보라.

해설 보기

2에서는 객체 의미를 약속된 Byte 표현으로 encode/serialize한다. 5에서는 받은 Byte를 parse/decode하여 애플리케이션 의미로 복원한다.

Q5. Shared Memory와 Message Passing 중 항상 우월한 방식이 없는 이유는?

해설 보기

Shared Memory는 동기화 복잡성이, Message Passing은 직렬화·지연·실패 문제가 중심이어서 요구사항과 경계에 따라 선택해야 한다.

12. 연구자의 관점

“네트워크가 느리다”를 한 덩어리로 보지 않고 메시지 크기, serialization, local queueing, network path, remote processing으로 나누어 관찰하는 습관이 중요하다. 이는 distributed tracing, RPC 성능 분석, failure diagnosis와 연결된다.

13. Research Question 후보

1단계에서는 RQ를 확정하지 않는다. 다만 “원격 요청 latency를 여러 처리 구간으로 어떻게 분해해 측정할 것인가?”라는 관점을 기억한다.

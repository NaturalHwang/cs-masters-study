1. 오늘의 주제

Sequential·Concurrent·Parallel의 차이, Running/Ready/Blocked 상태, Blocking I/O를 이해한다.

2. 학습 목표

  • Concurrency와 Parallelism 구분
  • Running/Ready/Blocked 상태 설명
  • Blocking I/O가 CPU 활용에 미치는 영향 설명
  • 동시성이 필요한 이유를 서버 예시로 설명

3. 이전 학습과의 연결

Day03의 Thread와 Context Switching을 이용해 여러 실행 흐름을 번갈아 진행할 수 있다. 오늘은 왜 그런 구조가 필요한지 본다.

4. 필요한 선수지식과 3~5분 복습

CPU는 한 코어에서 한 순간 하나의 실행 흐름을 수행한다고 단순화한다. I/O는 CPU 계산과 다른 장치·외부 시스템의 완료를 기다릴 수 있다.

5. 문제 상황

요청 A가 DB 응답을 100ms 기다리는 동안 CPU가 아무 일도 하지 않는다면, 독립적인 요청 B를 처리할 기회를 잃는다.

6. 핵심 개념

Sequential

한 작업을 끝낸 뒤 다음 작업 진행.

Concurrent

여러 작업이 시간상 겹쳐 진행되도록 관리되는 상태. 한 코어에서도 interleaving으로 가능하다.

Parallel

여러 작업이 실제 같은 시점에 여러 코어 등에서 실행된다.

Concurrency ≠ Parallelism. 동시성은 진행 구조, 병렬성은 실제 동시 실행이다.
상태의미
Running현재 CPU에서 실행 중
Ready실행 가능하지만 CPU 차례 대기
Blocked/WaitingI/O나 조건 등 외부 사건을 기다림
A Running → I/O 요청 → A Blocked
                         ↓
                  CPU가 B 실행
I/O 완료 → A Ready → 이후 다시 Running

7. 실제 시스템 사례

웹 서버가 네트워크·DB I/O를 기다릴 때 다른 요청을 처리하는 구조는 처리량과 자원 활용에 중요하다. Thread pool, event loop 등은 서로 다른 설계이며 오늘은 구현 세부를 다루지 않는다.

8. Trade-off와 대안

Concurrency는 대기 시간을 숨기고 활용도를 높일 수 있지만 scheduling·context switching·shared-state coordination 복잡성을 만든다. 무조건 더 많은 concurrency가 더 빠른 것은 아니다.

9. 간단한 심화

CPU-bound 작업은 코어 수와 병렬성이 중요하고, I/O-bound 작업은 기다리는 동안 다른 일을 진행하는 concurrency의 이점이 특히 크다.

10. 핵심 요약

  1. Sequential, Concurrent, Parallel은 다르다.
  2. Concurrent는 한 코어에서도 가능하다.
  3. Blocked 작업은 CPU를 사용할 수 없다.
  4. Ready 작업을 실행해 대기 시간을 활용할 수 있다.
  5. Concurrency는 성능 기회와 복잡성을 함께 만든다.

11. 확인 질문 3~5개와 접이식 해설

Q1 한 코어에서도 concurrency가 가능한가?

해설

가능하다. 실행을 interleave하면 여러 작업이 겹쳐 진행된다.

Q2 Ready와 Blocked 차이는?

해설

Ready는 CPU만 받으면 실행 가능, Blocked는 다른 사건이 먼저 완료돼야 한다.

Q3 Parallelism은 언제 성립하는가?

해설

여러 실행이 실제 같은 시점에 여러 실행 자원에서 수행될 때.

Q4 3~5분 실행 추적

t=0 A Running
t=2 A DB I/O 요청
t=2~8 ?
t=8 A I/O 완료

B가 Ready라면 t=2~8에 어떤 상태 전이가 가능한가?

해설

A는 Blocked, B는 Running이 될 수 있다. A의 I/O 완료 후 A는 Ready로 돌아간다.

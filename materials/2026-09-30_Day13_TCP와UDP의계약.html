1. 오늘의 주제

TCP(Transmission Control Protocol)와 UDP(User Datagram Protocol)가 애플리케이션에 제공하는 서로 다른 전송 계약을 비교한다. 핵심은 TCP Byte Stream, UDP Datagram, 순서, 손실, 재전송, 메시지 경계다.

2. 학습 목표

  • TCP의 Byte Stream과 UDP의 Datagram 모델을 설명한다.
  • TCP의 Sequence Number, ACK, Retransmission이 필요한 이유를 설명한다.
  • UDP가 메시지 경계를 유지하지만 순서·전달·재전송을 보장하지 않음을 설명한다.
  • TCP 전송 성공과 애플리케이션 업무 처리 성공을 구분한다.

4. 필요한 선수지식과 3~5분 복습

Byte

애플리케이션 데이터는 네트워크 전송 시 byte들의 형태로 표현된다.

Packet

IP Packet은 목적지로 전달되지만 손실되거나 순서가 바뀔 수 있다.

ACK

Acknowledgment는 수신 진행 상태를 송신 측에 알려주는 신호다.

Protocol

양쪽이 같은 방식으로 데이터를 해석하고 예외 상황을 처리하기 위한 규칙이다.

5. 먼저 제시하는 문제 상황

송신 애플리케이션이 TCP 연결에서 아래처럼 두 번 쓴다고 하자.

send("ABC")
send("DEF")

수신 측이 반드시 recv() → "ABC", 그 다음 recv() → "DEF"를 얻는 것은 아니다. TCP는 메시지 목록이 아니라 Byte Stream을 제공하므로 다음처럼 읽힐 수도 있다.

recv() → "ABCDEF"

또는

recv() → "AB"
recv() → "CDEF"

반대로 UDP는 한 Datagram의 경계를 유지하지만, 그 Datagram이 반드시 도착하거나 전송 순서대로 도착한다는 계약은 제공하지 않는다.

6. 핵심 개념

6.1 TCP = Byte Stream

TCP 연결에서 애플리케이션은 순서 있는 byte의 흐름을 읽고 쓴다. 송신 측의 개별 send 호출 경계는 수신 측 read/recv 경계로 보존되지 않는다.

Application write: "ABC" + "DEF"
TCP stream:        A B C D E F

6.2 Sequence Number

TCP는 데이터 byte의 위치를 식별하기 위해 sequence number를 사용한다. 네트워크에서 segment 순서가 바뀌더라도 올바른 순서의 stream을 구성하는 데 필요하다.

먼저 도착: bytes 110~119
나중 도착: bytes 100~109

TCP가 애플리케이션에 제공하려는 순서:
100 ... 109, 110 ... 119

6.3 ACK와 Retransmission

손실이 가능한 네트워크 위에서 TCP는 전송 상태를 추적하고, 필요한 경우 재전송(Retransmission)하여 stream을 복원한다.

Sender              Receiver
100~109 ----------> 수신
       <------------ ACK
110~119 ----X       손실
110~119 ----------> 재전송
       <------------ ACK

6.4 UDP = Datagram

UDP는 애플리케이션이 보낸 Datagram을 메시지 단위로 다룬다. 하지만 TCP처럼 연결 상태를 유지하며 byte sequence와 재전송을 관리하지 않는다.

sendto("ABC") → Datagram 1
sendto("DEF") → Datagram 2

메시지 경계는 구분되지만
도착 여부와 도착 순서는 별도 보장 없음

7. 실제 시스템 사례

TCP에서는 애플리케이션이 Message Boundary를 정의해야 한다

JSON 두 개를 TCP로 연속 전송해도 수신 recv() 한 번에 JSON 하나가 정확히 대응된다고 가정하면 안 된다.

// length-prefix 예
[length][payload][length][payload]

// delimiter 예
message1\n
message2\n

재고 예약의 계층 구분

Client
  ↓ bytes
TCP
  ↓
Server TCP stack
  ↓
Server Application
  ↓
Database Transaction / Commit

TCP ACK와 서버 애플리케이션의 처리 완료, DB commit은 서로 다른 사건이다. 업무 수준 중복 방지는 이후 Idempotency와 Transaction 주제에서 다시 다룬다.

8. Trade-off와 대안

선택장점대가
TCP순서 있는 신뢰성 있는 stream, 손실 복구를 transport가 담당연결 상태 관리, 메시지 경계는 애플리케이션이 정의
UDPDatagram 경계, 단순한 transport 동작필요한 순서·재전송·중복 처리를 상위 계층에서 설계

“TCP가 항상 더 좋다” 또는 “UDP가 항상 더 빠르다”가 아니라 애플리케이션의 delivery semantics와 latency 요구를 먼저 정해야 한다.

9. 간단한 심화

Segment ≠ Application Message

TCP 구현은 segment를 사용하지만 애플리케이션의 핵심 추상화는 byte stream이다.

ACK의 의미

TCP ACK는 transport 계층 수신 상태에 관한 신호이지 애플리케이션 업무 완료를 뜻하지 않는다.

연결 실패 가능성

TCP도 영원한 전달을 약속하지 않는다. 재전송 후 연결이 실패할 수 있으며 애플리케이션은 오류와 미확정 업무 상태를 처리해야 한다.

10. 핵심 요약

  1. TCP는 메시지가 아니라 순서 있는 Byte Stream을 제공한다.
  2. Sequence Number·ACK·Retransmission은 손실·재정렬 위에서 stream을 복원하는 핵심 메커니즘이다.
  3. UDP는 Datagram 경계를 유지하지만 전달·순서·재전송을 자체 보장하지 않는다.
  4. TCP를 쓰더라도 application message framing이 필요하다.
  5. TCP 전달 성공과 Exactly-once business processing은 다른 문제다.

11. 확인 질문 3~5개와 접이식 해설

Q1. TCP에서 send 두 번이 recv 두 번과 1:1 대응하는가?

해설 보기

아니다. TCP는 Byte Stream이라 호출 경계가 보존되지 않는다.

Q2. UDP의 Datagram 경계 유지가 전달 보장을 의미하는가?

해설 보기

아니다. 메시지 단위와 신뢰성은 별도 개념이다.

Q3. TCP ACK를 받으면 서버 DB commit 성공으로 봐도 되는가?

해설 보기

안 된다. Transport 수신과 Application 처리, Durable Commit은 구분해야 한다.

Q4. 3~5분 실행 추적

bytes 110~119가 먼저 도착하고 100~109가 나중에 도착했다. 연결이 정상 유지되고 모든 byte가 수신되었다면 애플리케이션에는 어떤 순서로 제공해야 하는가?

해설 보기

100~119의 올바른 stream 순서로 제공해야 한다. 네트워크 도착 순서 그대로 노출하는 것이 TCP 계약이 아니다.

Q5. 설계 비교

실시간 위치처럼 오래된 값의 복구보다 최신 값이 중요한 경우에도 모든 과거 데이터의 순서 있는 재전송이 항상 최우선일까?

해설 보기

아니다. 요구사항에 따라 최신성·낮은 지연이 더 중요할 수 있으므로 프로토콜 선택은 의미와 trade-off를 기준으로 해야 한다.

12. 연구자의 관점

  • Transport reliability와 application correctness를 별도 측정해야 한다.
  • “전송됨·수신됨·처리됨·영속화됨”을 서로 다른 이벤트로 모델링해야 한다.
  • Framing 오류는 네트워크 장애 없이도 protocol bug를 만들 수 있다.
  • 복구 전략이 latency와 correctness에 미치는 효과를 각각 평가해야 한다.

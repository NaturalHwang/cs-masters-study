1. 오늘의 주제

동시성(Concurrency)이 왜 어려운지 작은 실행을 추적하며 확인한다. 핵심은 경쟁 조건(Race Condition), Read-Modify-Write, 원자성(Atomicity), 불변식(Invariant)이다.

2. 학습 목표

  • x = x + 1 같은 한 줄이 실제로 여러 단계로 실행될 수 있음을 설명한다.
  • Race Condition이 실행 순서에 따라 결과가 달라지는 문제임을 확인한다.
  • Atomicity가 필요한 이유를 설명한다.
  • 재고가 음수가 되지 않아야 한다 같은 Invariant를 동시성 문제와 연결한다.

4. 필요한 선수지식과 3~5분 복습

Shared Memory

같은 프로세스의 Thread들은 Code/Data/Heap의 많은 부분을 공유하므로 같은 변수 stock에 접근할 수 있다.

Context Switching

Thread A가 작업을 끝내기 전에 CPU가 Thread B로 전환될 수 있다.

Invariant

오늘의 Invariant: 재고(stock)는 0보다 작아지면 안 되고, 성공한 예약 수는 실제 판매 가능한 수량을 넘으면 안 된다.

5. 먼저 제시하는 문제 상황

재고가 1개 남았고 두 사용자가 거의 동시에 예약을 요청한다.

stock = 1

if stock > 0:
    stock = stock - 1
    예약 성공
순서Thread AThread Bstock
1read → 11
2read → 11
3재고 있음 판단1
4재고 있음 판단1
5write 00
6write 00

최종 stock은 0이지만 예약은 두 건 성공할 수 있다. 코드 한 줄씩 보면 정상이어도 전체 실행은 잘못될 수 있다.

6. 핵심 개념

6.1 Read-Modify-Write

counter = counter + 1

1. counter 읽기
2. 1 더하기
3. 결과 쓰기

소스 코드 한 줄이 실행의 한 단위라는 보장은 없다.

6.2 Lost Update

순서ABcounter
1read 1010
2read 1010
3calculate 1110
4calculate 1110
5write 1111
6write 1111

두 번 증가했는데 결과는 11이다. 하나의 갱신이 사라졌다.

6.3 Race Condition

Race Condition은 여러 실행 흐름이 공유 상태에 접근할 때 어떤 interleaving이 발생하느냐에 따라 프로그램의 결과나 올바름이 달라지는 상황이다.

6.4 Atomicity

Atomicity는 어떤 작업이 중간 상태로 쪼개져 다른 실행이 끼어든 것처럼 보이지 않고 하나의 논리적 단위처럼 수행되는 성질이다.

“한 줄 코드 = atomic”은 아니다. Atomic한지는 언어, CPU 명령, 런타임, 동기화 방법에 따라 달라진다.

6.5 Invariant

Invariant는 시스템이 올바른 상태라면 항상 지켜져야 하는 조건이다. 동시성 제어의 목적은 단순히 직렬화하는 것이 아니라 필요한 Invariant를 지키는 것이다.

7. 실제 시스템 사례

if (inventory.getStock(productId) > 0) {
    inventory.decrease(productId);
    reservation.create(...);
}

여러 요청을 여러 Thread가 처리하면 조회와 변경 사이에 다른 요청이 끼어들 수 있다. 한 프로세스 내부에서는 Mutex/Lock이나 Atomic primitive, DB에서는 Transaction/Locking/MVCC/조건부 UPDATE 등이 사용될 수 있다.

오늘은 해결책 자체보다 문제를 정확히 보는 데 집중한다.

8. Trade-off와 대안

접근장점대가
동기화 없음제어 비용이 적고 병렬성 확보 가능Race Condition 가능
모든 작업 직렬화이해와 correctness 확보가 쉬움처리량 저하 가능
필요 구간만 보호Correctness와 Concurrency 균형보호 범위를 설계하기 어려움

9. 간단한 심화

Atomicity와 Visibility는 다르다. Atomicity는 작업이 쪼개져 보이는가의 문제이고, Visibility는 한 Thread가 쓴 값을 다른 Thread가 언제 볼 수 있는가의 문제다.

10. 핵심 요약

  1. 공유 변수를 다루는 한 줄의 코드도 여러 단계로 실행될 수 있다.
  2. Race Condition은 실행 순서에 따라 correctness가 달라지는 문제다.
  3. Read-Modify-Write가 섞이면 Lost Update가 생길 수 있다.
  4. Atomicity는 필요한 작업을 하나의 논리적 단위처럼 보이게 하는 성질이다.
  5. 동시성 제어의 최종 목적은 Invariant를 지키는 것이다.

11. 확인 질문 3~5개와 접이식 해설

Q1. 왜 x++가 한 줄이라는 사실만으로 atomic하다고 말할 수 없는가?

해설 보기

읽기, 계산, 쓰기 등 여러 단계로 나뉠 수 있고 그 사이 다른 실행이 끼어들 수 있기 때문이다.

Q2. Race Condition과 “Thread가 여러 개 존재한다”는 왜 같은 말이 아닌가?

해설 보기

Thread가 여러 개 있어도 공유 상태를 위험하게 수정하지 않거나 적절한 동기화를 하면 Race Condition이 없을 수 있다. 결과가 실행 순서에 의존하는지가 핵심이다.

Q3. 재고 시스템의 Invariant를 한 문장으로 써보라.

해설 보기

예: 어떤 실행 순서에서도 성공한 예약 수가 판매 가능한 재고를 초과하지 않아야 한다.

Q4. 실행 추적

초기값 counter = 5에서 A와 B가 각각 counter = counter + 1을 실행한다. 최종값이 6이 되는 interleaving을 적어보라.

해설 보기
A: read 5
B: read 5
A: calculate 6
B: calculate 6
B: write 6
A: write 6

정상적인 직렬 실행이면 7이어야 한다.

Q5. 큰 Lock과 작은 Lock 범위의 trade-off는?

해설 보기

큰 Lock은 correctness를 이해하기 쉽지만 불필요한 직렬화를 만들 수 있고, 작은 Lock은 concurrency를 높일 수 있지만 보호 범위를 잘못 잡으면 Invariant가 깨질 수 있다.

12. 연구자의 관점

  • Correctness vs Performance: 보호를 강하게 할수록 병목이 생길 수 있다.
  • Bug Reproducibility: race bug는 특정 timing에서만 나타나 재현이 어렵다.
  • Observability: 어떤 interleaving이 있었는지 추적하기 어렵다.

이후 Software Engineering에서는 concurrency bug detection, deterministic replay, testing 같은 주제로 연결될 수 있다.

1. 오늘의 주제

Day06에서 공유 변수에 대한 Read-Modify-Write가 서로 섞이면 결과가 틀릴 수 있음을 확인했습니다. 오늘은 그 문제를 해결하기 위한 가장 기본적인 도구인 임계 구역(Critical Section), 상호 배제(Mutual Exclusion), 뮤텍스(Mutex/Lock)를 배웁니다.

핵심 방향: “Lock을 쓴다”가 목적이 아니라, Invariant를 깨뜨릴 수 있는 구간을 정확히 찾아 그 구간의 동시 실행을 제한한다가 목적입니다.

2. 학습 목표

  • Critical Section을 공유 상태의 올바름 관점에서 설명할 수 있다.
  • Mutual Exclusion이 무엇을 보장하고 무엇을 자동으로 보장하지 않는지 설명할 수 있다.
  • Mutex의 lock/unlock 흐름을 작은 실행으로 추적할 수 있다.
  • Lock 범위가 너무 좁거나 너무 넓을 때 각각 어떤 문제가 생기는지 비교할 수 있다.

3. 이전 학습과의 연결

Day06의 문제는 다음과 같았습니다.

Shared Memory + Interleaving ↓ Read → Modify → Write가 서로 섞임 ↓ Race Condition / Lost Update ↓ Invariant 위반 가능

오늘은 이 흐름에서 “어떤 코드 구간을 한 번에 한 Thread만 통과시키면 Invariant를 지킬 수 있는가?”를 다룹니다.

4. 필요한 선수지식과 3~5분 복습

4.1 Atomicity

여러 단계의 작업이 다른 실행과 중간에 섞이지 않고 하나의 논리적 단위처럼 보여야 할 때 원자성(Atomicity)이 필요합니다.

4.2 Invariant

재고 예약 서비스의 예:

Invariant: 성공한 예약 수는 판매 가능한 재고를 초과하면 안 된다.

4.3 Interleaving

한 Thread가 소스 코드 한 줄을 “완전히 끝낸 뒤에만” 다른 Thread가 실행된다고 가정할 수 없습니다. Scheduler와 CPU 실행은 더 작은 단계 사이에서 실행을 전환할 수 있습니다.

오늘의 깊이 제한: Lock 구현에 쓰이는 test-and-set, compare-and-swap, spinlock, memory barrier는 오늘 상세히 다루지 않습니다. 먼저 Lock을 사용하는 쪽의 의미를 정확히 잡습니다.

5. 먼저 제시하는 문제 상황

재고가 1개이고 두 Thread가 같은 함수를 실행한다고 합시다.

if stock > 0:
    stock = stock - 1
    reservationCount = reservationCount + 1

여기서 보호해야 할 것은 단순히 stock = stock - 1 한 줄일까요?

아닙니다. 재고 확인과 감소가 하나의 판단 단위라면, 그 사이에 다른 Thread가 끼어들면 여전히 두 요청이 모두 “재고 있음”으로 판단할 수 있습니다.

보호 범위문제
감소 한 줄만 보호재고 확인은 Lock 밖에서 동시에 수행될 수 있어 잘못된 판단 가능
확인+감소를 함께 보호두 Thread가 같은 시점의 재고를 근거로 동시에 성공 판단하는 것을 막을 수 있음

6. 핵심 개념 — 직관 → 예 → 정의 → 동작

6.1 Critical Section — “동시에 들어가면 안 되는 코드 구역”

임계 구역(Critical Section)은 공유 상태를 읽거나 변경하는 코드 중, 여러 실행 흐름이 동시에 수행하면 올바름이 깨질 수 있어서 동시 실행을 제어해야 하는 구간입니다.

중요한 점은 Critical Section이 “공유 변수를 만지는 모든 코드”와 정확히 같은 말은 아니라는 것입니다. 어떤 Invariant를 지켜야 하는지에 따라 보호 범위를 정해야 합니다.

6.2 Mutual Exclusion — 한 번에 하나만

상호 배제(Mutual Exclusion)는 특정 Critical Section에 같은 시점에 둘 이상의 Thread가 들어가지 못하도록 하는 성질입니다.

Thread A ---- lock 획득 ---- [ Critical Section ] ---- unlock ---- Thread B ---- lock 시도 ---- [ 기다림 ] ---- lock 획득 ...

이렇게 하면 Critical Section 내부의 실행은 Thread A와 B 사이에서 겹치지 않습니다.

6.3 Mutex

Mutex는 Mutual Exclusion을 제공하기 위해 사용하는 대표적인 Lock 객체입니다. 개념적으로 상태는 다음처럼 볼 수 있습니다.

UNLOCKED --lock()--> LOCKED(owner=A) LOCKED --unlock()--> UNLOCKED

다른 Thread가 이미 소유한 Mutex를 획득하려 하면 일반적인 blocking mutex에서는 사용할 수 있게 될 때까지 기다릴 수 있습니다. 실제 세부 동작은 mutex 종류와 구현에 따라 달라질 수 있습니다.

6.4 작은 재고 예제

lock(mutex)
try:
    if stock > 0:
        stock = stock - 1
        reservationCount = reservationCount + 1
finally:
    unlock(mutex)

여기서 Lock의 목적은 코드 모양을 바꾸는 것이 아니라, 재고 확인→상태 변경이 다른 Thread와 섞이지 않도록 하여 Invariant를 지키는 것입니다.

6.5 실행 추적

순서Thread AThread BMutexstock
1lock 획득A 소유1
2stock 읽음 → 1lock 시도A 소유, B 대기1
3stock=0대기A 소유0
4unlock대기/획득 가능해제0
5lock 획득 후 stock 읽음 → 0B 소유0
6예약 거절, unlock해제0

두 Thread가 모두 Critical Section에 들어가긴 하지만 동시에 들어가지는 않았습니다.

7. 실제 시스템 사례

POSIX Threads의 pthread_mutex_lock()은 mutex를 잠그고, 다른 Thread가 이미 소유 중이면 mutex가 사용 가능해질 때까지 호출 Thread가 block될 수 있습니다. pthread_mutex_unlock()은 mutex를 해제합니다. 대기 중인 Thread가 여러 개일 때 다음 소유자를 누가 되는지는 scheduling policy의 영향을 받습니다.

pthread_mutex_lock(&mutex);
/* critical section */
stock--;
pthread_mutex_unlock(&mutex);
학습용 모델과 실제 시스템 구분: 위 코드는 “mutex로 임계 구역을 감싼다”는 의미를 보여주는 최소 예입니다. 실제 운영 코드는 error handling, cancellation, lock ordering, 데이터 소유권 등을 더 고려해야 합니다.

8. Trade-off와 대안

설계얻는 것대가
Lock 없음동시 실행 제한이 적음Race Condition으로 correctness 깨질 수 있음
아주 큰 Lock 범위올바름을 추론하기 쉬운 경우가 많음독립 작업도 함께 직렬화되어 concurrency 감소
필요한 상태 전이만 LockCorrectness와 concurrency 균형 가능정확한 보호 범위를 찾기 어려움
공유 상태 자체를 줄임Lock 필요성·경쟁 감소 가능데이터 복사·메시지 전달·설계 변경 비용 가능

좋은 Lock 설계는 “Lock을 최대한 많이 건다”가 아니라, 필요한 Invariant를 만족하면서 경쟁이 불필요한 부분은 함께 실행될 수 있게 하는 것입니다.

9. 간단한 심화 — Lock 범위와 책임 경계

다음 두 코드를 비교해봅시다.

// 너무 좁을 수 있는 범위
if stock > 0:
    lock(mutex)
    stock--
    unlock(mutex)
// Invariant 기준으로 더 타당할 수 있는 범위
lock(mutex)
if stock > 0:
    stock--
unlock(mutex)

두 번째는 “재고를 보고 판단하는 순간”과 “재고를 바꾸는 순간”을 같은 보호 구역에 둡니다. 이것이 check-then-act 패턴에서 중요한 이유입니다.

주의: Mutex 하나를 썼다고 모든 동시성 문제가 자동으로 해결되는 것은 아닙니다. 잘못된 Lock 선택, 잘못된 범위, 여러 Lock 사이 순서 문제는 이후 Deadlock과 연결됩니다.

10. 핵심 요약

  1. Critical Section은 동시에 실행되면 공유 상태의 올바름이 깨질 수 있는 코드 구역이다.
  2. Mutual Exclusion은 해당 구역에 한 번에 하나의 Thread만 들어가도록 하는 성질이다.
  3. Mutex는 Mutual Exclusion을 제공하는 대표적인 Lock 도구다.
  4. Lock 범위는 소스 코드 줄 수가 아니라 지켜야 할 Invariant를 기준으로 정해야 한다.
  5. 너무 큰 Lock은 concurrency를 줄이고, 너무 작은 Lock은 Race Condition을 남길 수 있다.

11. 확인 질문 3~5개와 접어서 보는 해설

Q1. Critical Section은 “공유 변수를 쓰는 한 줄”과 항상 같은가?

해설 보기

아니다. 공유 상태의 Invariant를 지키기 위해 하나의 논리적 상태 전이로 묶여야 하는 범위가 Critical Section이 될 수 있다. 예를 들어 재고 확인과 감소는 서로 다른 두 줄이어도 함께 보호해야 할 수 있다.

흔한 오해: write 연산만 잠그면 항상 충분하다고 생각하는 것.

Q2. Mutual Exclusion이 보장되면 프로그램 전체가 병렬로 실행되지 않는가?

해설 보기

아니다. 같은 Mutex로 보호된 Critical Section만 동시에 들어가지 못한다. Lock 밖의 독립적인 코드는 다른 Thread와 동시에 진행될 수 있다.

Q3. Mutex가 이미 다른 Thread에 의해 잠겨 있으면 일반적인 blocking mutex에서 어떤 일이 일어날 수 있는가?

해설 보기

호출 Thread는 mutex가 사용 가능해질 때까지 block될 수 있다. 정확한 동작은 mutex 종류와 구현에 따라 달라질 수 있다.

Q4. 3~5분 실행 추적

초기 stock=1. A와 B가 같은 Mutex를 사용합니다. 아래 빈칸의 상태를 직접 채워보세요.

순서ABMutex ownerstock
1lock 성공?1
2stock 읽기lock 시도?1
3stock=0??0
4unlock??0
5stock 읽기 → 0?0
실행 추적 해설 보기

1: owner=A. 2: owner=A이고 B는 대기. 3: B 대기, owner=A. 4: A가 해제하면 B가 이후 획득 가능. 5: owner=B. B는 stock=0을 본 뒤 예약을 성공시키면 안 된다.

Q5. 설계 비교 — Lock을 함수 전체에 걸기 vs 재고 상태 전이 부분에만 걸기

해설 보기

함수 전체 Lock은 이해하기 쉬울 수 있지만 logging, 포맷팅, 독립 계산처럼 공유 상태 보호와 무관한 작업까지 직렬화할 수 있다. 상태 전이 부분만 보호하면 concurrency가 좋아질 수 있지만 범위를 잘못 줄이면 Race Condition이 남는다. 핵심 기준은 Invariant다.

12. 연구자의 관점

  • Correctness specification: Lock 구현 전에 어떤 Invariant와 허용 가능한 interleaving을 정의해야 하는가?
  • Contention: 여러 Thread가 같은 Lock을 자주 원하면 대기 시간이 어떻게 커지는가?
  • Granularity: coarse-grained lock과 fine-grained lock 사이에서 correctness·throughput·복잡성이 어떻게 달라지는가?
  • Debuggability: 실제 race bug에서 “보호해야 할 상태 전이”를 어떻게 찾아낼 것인가?

이 관점은 이후 Software Engineering의 concurrency testing, static/dynamic race detection, observability와 자연스럽게 연결됩니다.

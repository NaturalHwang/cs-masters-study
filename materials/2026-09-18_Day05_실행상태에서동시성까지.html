5. 문제 상황

재고 예약 서버가 실행되고 요청 A와 B가 들어온다. A는 DB I/O를 기다린다. 이때 서버가 B를 처리하려면 Day01~04의 개념이 모두 필요하다.

6. 핵심 개념

SSD의 inventory-server
        ↓ OS 실행 준비
Process
 ├─ Address Space
 │   ├─ Code/Data/Heap
 │   ├─ Thread A Stack
 │   └─ Thread B Stack
 ├─ Thread A Running
 │      ↓ DB I/O
 │   Thread A Blocked
 └─ Thread B Ready → Running

Process Isolation은 다른 Process와 경계를 만들고, 같은 Process의 Thread들은 많은 데이터를 공유한다. 각 Thread는 개별 Stack/Register Context를 가져 실행을 이어간다.

7. 실제 시스템 사례

일반적인 백엔드 서버에서는 요청 처리와 network/DB I/O가 섞인다. 실제 framework의 threading/event-loop model은 다를 수 있지만, “실행 상태·대기·다른 작업 실행”이라는 기본 모델은 분석에 유용하다.

8. Trade-off와 대안

설계 선택장점대가
Process 분리강한 격리통신·관리 비용
Thread 공유빠른 공유·낮은 중복Race 위험
높은 ConcurrencyI/O 대기 활용스케줄링·동기화 복잡성

9. 간단한 심화

Week 2부터 “공유 메모리 + interleaving”이 실제 오류를 만드는 과정을 본다. 아직 Lock을 해결책으로 먼저 외우지 않고, 잘못된 실행을 먼저 추적한다.

10. 핵심 요약

  1. Program은 실행되며 Process가 된다.
  2. Process는 Address Space로 메모리 세계를 본다.
  3. Thread들은 Process 자원을 공유하면서 각자 실행 문맥을 가진다.
  4. Blocked I/O 동안 다른 Ready Thread를 실행할 수 있다.
  5. 공유+동시성은 Week 2의 Race Condition으로 이어진다.

11. 확인 질문 3~5개와 접이식 해설

Q1 Program과 Process를 연결해 설명하라.

해설

OS가 실행 환경과 상태를 준비하면서 정적 Program이 실행 중 Process로 동작한다.

Q2 Process Isolation과 Thread 공유는 모순인가?

해설

아니다. Process끼리는 기본 격리되고, 같은 Process 안 Thread들은 그 Process의 주소 공간을 공유한다.

Q3 Blocked와 Ready의 차이는?

해설

Blocked는 외부 사건 대기, Ready는 CPU만 기다리는 상태.

Q4 종합 실행 추적

시각AB
0RunningReady
2DB I/O 요청Ready
3~7??
8I/O 완료Running 가능
해설

3~7 동안 A=Blocked, B=Running이 가능하다. 8에 A는 Ready가 되고 scheduler 선택에 따라 이후 Running이 된다.

Q5 다음 주 예측

A와 B가 같은 stock을 동시에 수정하면 어떤 문제가 생길 수 있는가?

해설

실행 순서에 따라 결과가 달라지는 Race Condition 가능성이 생긴다.
